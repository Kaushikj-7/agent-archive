# Muse runtime, version and skills boundaries

The runtime [presence qualification](runtime-presence.md) remains authoritative.
A root shell observation does not establish child, resume or monitor identity.
`MUSE_THREAD_ID` identifies the running chat in the documented contract;
`MUSE_SESSION_ID` refers to its root. Equal root IDs must not become a child
contract, and inventory must not substitute for independently qualified identity.
Production selection remains unknown until that qualification is available.

The pure version parser accepts the observed native output shape
`Muse Code 1.4.9 (1.4.9-R6297.1)`. It separates release `1.4.9` and display build
`1.4.9-R6297.1`; neither value is an executable SHA. Contradictory release/build
versions, additional output, control characters and unknown forms are refused.
An installed executable observation cannot stamp a child conversation's version.
The registered installed version probe uses the injected PATH lookup and fixed
`--version` operation, with `MUSE_NO_AUTO_UPDATE=1`, the existing two-second
deadline and a strict 4096-byte output cap. A fake executable verifies argv,
environment preservation and refusal of overlong/multiline output; no native
Muse process was run for these tests. Unrecognized output stays unknown.

The skill provider uses the existing shared `.agents/skills` destination and
ownership/expected-byte planner. It declares user/project shared and foreign roots separately, with config-local
and Codex roots resolved only from the fixed two-variable environment snapshot.
The caller additionally qualifies the effective data home once through the
existing native-location policy, shared by canonical Muse aliases. The exact
builtin root is `muse/skills/bundled/muse-core/skills` under that base; an absent
or invalid base supplies no builtin root. It never runs `muse skills` or changes native settings,
activation, hooks or MCP entries. Foreign and nonregular files are preserved.
Shared installation must be deduplicated with Codex and Cursor by the existing
installation transaction.

The [official skills guide](https://meta-models.github.io/muse-code-sdk/next/guides/extend/skills/)
documents additional config-local, foreign and plugin sources. Project trust and
activation affect availability; foreign personal roots have configuration and
rollout gates. Config-local and foreign filesystem inventory now uses exact injected locations;
project trust and native activation remain unknown. The builtin filesystem layout was observed in the isolated pinned native
1.4.9-R6297.1 case, and is now declared explicitly. The private provider-free native-local install experiment qualified the exact
version1 `muse/plugins/installed.json` wire locator and relative digest-addressed
cache layout. Production interprets only that observed `muse`/`native-local`
subset, verifies the raw cached manifest hash and observes declared skill files.
Unknown provenance, versions and authority fields remain incomplete; no scratch
package is treated as an installed plugin. The existing
observer supports finite tagged manifest-file declarations, preserving package
confinement, installed-only coverage, physical-read deduplication and one shared
byte/declaration allowance. The registry/manifest bytes share its per-call allowance and are never retained
in uploaded evidence. Package scope is the stable logical `muse-plugin:<id>`;
raw package digests stay private and do not claim whole-package verification.
Private owned/no-symlink registry, manifest, body and ancestor checks fail closed;
ownership qualification is unavailable on unsupported platforms. Production observation never
executes native CLI commands.
Inventory proves installation; it does not prove eligibility, invocation or a
read. Unknown coverage must remain unavailable, never observed-no-use. Optional metadata installed declaration identities preserve logical scope/id
provenance when multiple declarations share a name and filtered content hash.
They remain attached to the existing content group and do not create duplicate
legacy rows, eligible coverage or use. Muse parser0.7.0 stamps this derivation;
other agent/default parser versions are unchanged. Positive native read evidence
requires exact owning conversation and skill identity; a content-hash association
requires additional privacy-safe byte-domain qualification.

The closed native `runtime.session` schema1/run event `skill_read_observed`
with exactly `skill_id`, `evidence_kind: read_skill_tool`, `evidence_hash` and
`observed_at_sequence` is supported as an explicit native harness read report.
The pinned1.4.9-R6297.1 isolated controlled read corroborated the historical
1.4.8 event: native ID equaled the installed inert `pr10-local` ID, sequence
equaled the event's own run-source sequence, and the prefixed SHA256 decoded to
the exact102-byte skill file hash rather than the969-byte rendered tool result.
No tool-result numeric join was established. This shape must still pass the
complete owning-source, materialized own-run, unique source and increasing
sequence validators. IDs are bounded portable lowercase logical tokens;
case/path/namespace aliases, extra keys, unknown tags and invalid types refuse.

Production validates the exact `sha256:<64lowerhex>` native hash then erases
it. Shared filesystem snapshots hash redacted file bytes, so the original-byte
native digest cannot safely be retained or associated by name/hash alone.
The existing `NativeSkillUses`/`SkillUse` path derives `native_invocation`: the
native harness explicitly reports a skill read. A leased content-only companion
may add the existing safe SHA256 from an actual authorized observer read only
when full RedactText leaves bytes unchanged and no literal `[REDACTED]` occurs.
It compares no original digest from rejected/redacted candidates and creates no
native-ID/install-name alias. Private native hashes are erased on terminal
operation/release. Evidence alone is cached per user/own-project pass; private
safe digests belong only to the actual cache-miss observation and its callback
view through Finalize or error. The first user/project reads may both match;
a later new project can match only its newly read content. Cache hits remain
hashless without filesystem rereads. Optional capacity refusal drops the whole
current companion without withholding ordinary evidence or changing scope
pressure flags. Finalize preflights optional scratch and encoding capacity before
mutation and preserves the exact restored output when either does not fit.
Required Restore and source/output/cancellation failures remain strict. Exact
prior-event proof restores before the activity probe without filesystem work;
only the existing active observation gate can add proof. The
closed eight/ten-field variant uses existing producer-evidence trust, not
coherent-forgery authentication. This new implementation checkpoint still needs
fresh deterministic and actual consumer qualification. It does
not infer eligibility, membership, activation, successful result status or
native failure/no-op behavior. Installed inventory, call/result bodies,
`read_file` and broad-read omission markers alone cannot create this evidence.
General redacted-content product read-hash association and origin qualification remain separate open requirements.
Older strict Muse retained readers refuse the new closed event variant.

## Validation scope

Deterministic parser and shared planner conformance tests use synthetic inputs.
They cannot qualify native trust/activation, failed/no-op skill behavior, child
identity or supported platforms. The controlled producer/diagnostic facts above
qualify only the stated native event grammar and byte-domain observation;
the same controlled source (145,600 bytes) passed complete uninstrumented production
Source/Filter, bundle Parse, two refilter/Parse/metadata rounds and exact positive
`pr10-local`/`native_invocation` evidence with SHA256 omitted on commit `44c6bd87`.
The known source checksum and same-descriptor identity remained stable; that
consumer ran no native producer or raw tool-result decoder and retained no raw
result reference. Original failed attempts and the lost original endpoint result
(969 bytes) remain distinct.
Exact-thread identity, eligible inventory and general redacted-content read-hash
association remain open. No capture or default setup enablement follows from
skill presence.
